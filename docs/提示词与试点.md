# 提示词与试点

本技能可以单项目使用；可选的多项目用法是“一个总控入口 + 各项目已有执行聊天和项目记录”。总控帮助汇总证据、识别冲突、提出下一步；实际治理仍逐项目调用单项目技能。它不是跨项目后台调度器，不会常驻、自动建窗、改名、归档或接入可选中央服务。安装技能不授予读写聊天或项目的权限，新设备也不继承旧设备批准。

下列提示词中的尖括号需要替换；不要把占位符当作真实项目路径、会话 ID 或授权。首次使用以只读盘点开始。

## 首次只读盘点

```text
$project-window-governance
本轮只读盘点一个项目：<项目名称>，实际目录：<目标设备上的真实路径>。
已知入口：<已有规则、任务台账、交接文件的准确位置；未知写未知>。
先确认项目归属、技能加载路径和当前实际工具。先读已知文件，按需定位小范围文件，不扫描整个硬盘、用户目录、知识库或所有项目，不读取私有会话数据库及完整聊天存档。
仅收集必要的窗口标题、真实 ID、状态、职责、任务和验证证据；工具读取范围不足时写明覆盖范围，没有实际验证的能力标“未验证”。没有工具时使用我提供的最小摘要，不编造会话 ID。
输出本项目的事实来源、任务与单一主责、重复派工或状态冲突、已验证通过/失败/未验证、尚缺授权和最小下一步。
本轮不写文件、不发送消息、不建窗、不改名、不归档、不提交代码、不安装依赖。需要后续操作时先列具体对象、影响和恢复办法供我审查。
```

## 总控入口

```text
你是我的项目治理总控入口。项目范围仅限我随后逐项给出的项目；沿用各项目已有台账、执行聊天和回执，不新建一套平行事实源。
先只读整理各项目已提供的最小摘要，分别记录实际目录、目标、任务、单一主责、真实会话 ID（未确认留待定）、验证证据、阻塞、授权和下一步。不要因为当前聊天挂载目录就判断项目归属。
治理时逐项目调用 $project-window-governance，先核对该项目规则；不把多个项目混成同一次写入，不重复派工。发现冲突先找证据，缺少信息说明未覆盖内容。
当前没有授权任何跨聊天发送、建窗、改名、归档、文件写入、Git 或外部服务动作。先输出按项目区分的建议与可审查操作清单。若之后批准具体操作，按该授权执行并核对实际结果；工具不支持则给我手动传递的最小摘要。
不建立常驻任务、不跨设备执行、不接可选中央服务、不读私有会话库。没有变化不反复汇报。
```

总控入口本身不必新建聊天，可使用用户选定的现有聊天。需要另建时由用户明确要求。真实项目数量与每轮读取范围由用户指定，不自动扩大到所有项目。

## 单项目治理示例

```text
$project-window-governance
请治理 <单个项目名称>，实际目录为 <真实项目目录>，本轮目标是 <具体目标>。
沿用 <现有任务台账路径> 与 <已有交接位置>；执行聊天为 <正式工具核实的真实 ID，尚未核实写待定>。
先检查任务状态、验收标准、当前主责、已批准的修改范围和验证证据；同一任务同一时刻只有一个主责，协作项单列，不能重复派工。
本轮允许的具体操作：<逐项准确写出；没有则写只读>。所有其他操作先给对象、影响、恢复办法，等待我批准。
按真实结果记录已验证通过、失败、未验证。只有项目已选用本技能任务卡格式且我批准写入时才使用 tasks.py，显式指定已有任务目录。
本轮 receipt_id 使用 <项目:任务:本轮稳定编号>；同次重试复用编号和内容。中断后用原编号 recover，冲突时停止写入并报告差异，不删日志、不换编号掩盖失败。
收尾给我成果路径、实际验证、未完成项及下一步；一轮结束不能自动写成项目完成。
```

项目有既有上报协议时，先读协议再确定编号及字段。本包的本地回执不能直接视为任何总控端已接收；也不能假定外部上报脚本已安装。暂停或结束的任务，须有用户真实恢复决定才能恢复，不能用回执顺便恢复状态。

## 没有跨聊天工具时手动传递

让执行聊天生成以下最小摘要，由用户检查后复制到总控；总控的任务建议也由用户按同样方式传回指定项目聊天。生成摘要不代表已发送。

```text
项目：<名称及实际目录>
来源：<已有台账/交接位置、提炼时间、实际覆盖范围>
聊天：<原始标题；正式工具返回的真实 ID；没有则写未确认>
任务：<已有任务编号、目标、验收标准>
主责：<唯一当前主责；其他参与者只列协作项>
状态：<事实状态；不根据标题推断>
成果：<文件位置或必要证据引用>
验证：<passed/failed/unverified/mixed；实际检查与证据>
授权：<已批准的具体操作和来源；未批准项>
回执：<本轮稳定 receipt_id；未产生写未产生>
阻塞与下一步：<最少必要内容>
运行项：<本轮核实到的后台项与停止办法；未核实写未验证>
```

不附完整聊天、原始工具响应、密码、Token、API Key、Cookie 或无关私人信息。路径只是来源位置，不代表另一设备已同步或能访问。

## 完全合成的演练：三个项目、五个任务

**下面全部为模拟数据，没有真实派工、真实会话 ID、实机工具验证或实际验收；模拟结果不能用于宣称试点通过。**甲、乙、丙都是虚构项目；主责名称也只是演练角色。

| 模拟项目 | 模拟任务 | 目标 | 唯一模拟主责 | 演练关注点 | 实际验证 |
|---|---|---|---|---|---|
| 甲项目 | 甲-01 | 核对入口说明 | 甲执行聊天 | 先确认真实目录与事实源 | 未验证 |
| 甲项目 | 甲-02 | 补齐验收标准 | 甲执行聊天 | 顺序处理，不能以草稿视为批准 | 未验证 |
| 乙项目 | 乙-01 | 核对页面修正证据 | 乙执行聊天 | 区分检查通过与用户验收 | 未验证 |
| 乙项目 | 乙-02 | 整理换窗交接 | 乙执行聊天 | 接手会话 ID 未确认就留待定 | 未验证 |
| 丙项目 | 丙-01 | 核对暂停任务 | 丙执行聊天 | 未有用户恢复决定就保持暂停 | 未验证 |

演练时可用 `模拟甲:甲-01:第1轮` 这样的编号说明稳定性，但不能把模拟回执写入真实项目。模拟中若同任务出现两个主责，先记录冲突并定位来源，再由有权决定的人确认；不能凭总控建议自动向聊天派工。各模拟会话 ID 均为“未确认”，不生成看似真实的 ID。

## 可选真实试点：先验证，再考虑中央服务

若准备推广到多个项目，可由用户选择 **3 个真实活跃项目、至少 5 个真实任务，持续 5—10 个工作日** 作为试点。现在不代选真实项目、不声称已经开始。三个项目分别核实目录、事实源、执行聊天、主责、授权与可检查的验收标准。

试点按现有项目结构执行，记录以下实际证据：

1. 每个项目能从已有记录复原当前任务和下一步，读取范围最小，未越过项目边界。
2. 至少五个真实任务持续保持单一主责，冲突被明确记录并按真实决定解决，没有重复派工。
3. 每轮结果区分通过、失败、未验证；未完任务保持真实状态，检查通过不冒充用户验收。
4. 回执编号稳定，同次重试不重复写入。若实际发生中断，记录原编号恢复结果；未发生就写“真实中断恢复未验证”，不得人为宣称通过。需要专门演练时另提具体方案与授权。
5. 无跨聊天工具时，用户手动传递最小摘要后仍可接续；工具缺失和手工环节均如实记录。
6. 没有自动改名、归档、建窗、越权写入、跨设备并发写入或外部上传。运行状态与能力没有实测的项目保留“未验证”。

期末只汇总真实成果、验证证据、阻塞、额外人工负担和剩余缺口，由用户决定是否继续、调整或停止试点。不能因模拟演练、安装成功或工作日到期就宣布通过。只有真实试点结果经用户确认后，才另行评估可选中央服务的协议、权限、数据最小化与接收验证；本包没有接通它。
