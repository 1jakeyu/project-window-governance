# 项目窗口与任务治理

让用户知道本项目正在做什么、由谁负责、哪些成果已验证，以及下一步在哪个窗口继续。按本轮需要完成治理，不要求先使用其他技能。

## 工作边界

- 先确认实际项目、目标和本轮授权；不能只按聊天挂载目录判断项目归属。项目有现行规则、任务台账、交接和回执时，先读已知入口并复用。
- 每个平台可有本项目的协调窗口，各平台共用同一套项目事实。同一任务只设一个当前主责，其他窗口承担明确协作项；遇到冲突先定位证据，不另造平行台账。
- 用户已有的具体授权持续有效。治理建议、任务卡和命令参数本身不构成授权；新建聊天、向其他聊天发消息、重命名、归档、文件写入和 Git 操作分别遵守用户与平台规则。
- 不硬设窗口数量，不强制新建审查窗口，不因标题、时间久或发生上下文压缩就归档。保留已有命名和目录，只有它们确实阻碍协作时才提出改动。
- 先读已知文件，再按文件名定位，最后才搜索必要的小目录；限定项目范围、条数和摘要长度。不得默认读取私有会话数据库、完整聊天日志、凭证或无关项目。

## 根据请求选择工作

| 请求 | 最少需要的工作 |
|---|---|
| 盘点窗口、清理职责 | 确认项目 → 读取必要窗口元数据与摘要 → 责任和冲突表 → 按已授权范围执行 |
| 维护任务、更新进度 | 读取现有任务与授权 → 核对状态和验收证据 → 更新同一任务 → 记录回执 |
| 换窗或阶段收尾 | 核对当前版本 → 保存最小交接 → 确认接手窗口和主责 → 验证记录可继续执行 |
| 跨平台协作 | 各平台只收集必要证据 → 汇入现有事实源 → 明确每项任务主责与回传位置 |

治理可以在当前窗口完成。只有用户明确要求创建新的聊天时才创建；明确要求向某聊天下发或回传消息时才发送。能力不存在或无法覆盖时说明具体缺口，不把准备好的草稿说成已下发。

## 1. 建立本轮事实

读本项目规则、当前计划或任务台账、最近有效交接及与本轮相关的成果。按需核对：

- 项目的实际路径、当前目标、版本或阶段；
- 已有事实源、任务主责、关联的真实会话 ID；
- 已验证通过、失败、未验证，以及用户验收是否另有要求；
- 已批准的具体操作、尚缺的批准和保护对象。

旧消息是证据线索，不能覆盖更新的用户决定或实际成果。来源不一致时把冲突写清，再做最小补查；没有覆盖到不能写“没有”。

## 2. 盘点窗口与职责

优先用当前平台正式提供的列表和读取工具。只取本项目候选窗口的标题、真实 ID、归属、状态、时间及必要摘要；读取正文时限制轮数和返回长度，并自行提炼，不保存完整工具响应或整段聊天。

按当前平台条件加载：

- [Codex 适配](adapters/codex.md)
- [Claude Desktop 适配](adapters/claude-desktop.md)
- [Hermes / OpenClaw 适配](adapters/hermes-openclaw.md)

盘点表最少包括：原始标题、真实 ID、平台、职责、当前任务或证据、建议动作及理由。区分“事实状态”和“建议动作”；改名或归档前列出准确对象、影响和恢复办法。已明确授权的动作直接执行并核对结果。

可使用离线整理工具，不用它获取聊天数据：

```text
python <技能目录>/scripts/scan_windows.py --project <实际项目目录> --input <最小窗口数据.json>
```

不传 `--out` 只输出结果；需要保存时把 `--out <本轮已选定的证据目录>` 加上。输入由 Agent 使用正式工具或用户明确提供的数据整理，采用白名单字段，格式见 Codex 适配。工具不会连接平台、读取私有数据库或打开记录里引用的聊天文件。输出必须保留来源和覆盖范围；列表上限、漏掉归档聊天或摘要不足时，不声称覆盖完整。

## 3. 维护任务

先沿用项目现有任务系统；下面的小工具仅在项目选用本技能任务卡格式时使用。所有命令显式传 `--dir <现有任务卡目录>`，不要因默认路径又创建一套管理目录。

```text
python <技能目录>/scripts/tasks.py --dir <现有任务卡目录> board
python <技能目录>/scripts/tasks.py --dir <现有任务卡目录> new --title <具体任务> --executor <主责>
python <技能目录>/scripts/tasks.py --dir <现有任务卡目录> start <任务ID> --window <负责窗口标题>
```

`new` 只建立草稿卡；执行前填写真实目标、可检查的验收标准、允许修改范围、依赖和授权来源。空复选框不是验收标准。一个窗口可以顺序处理多个任务，一个任务可有协作窗口，但同一时刻只有一个主责，不能重复派工或多人无协调地覆盖同一文件。

状态表示任务事实：

- `待启动 / 进行中 / 有阻塞 / 已暂停 / 待验收`：依实际进展记录；一轮聊天结束不等于任务完成。
- `已完成 / 已取消`：需要真实用户决定，不能从程序检查通过推导。
- 暂停或已结束任务要重启时，记录真实用户恢复决定，再执行 `resume <任务ID> --by-user` 回到待启动，重新核对标准后 `start`；不能用回执顺便恢复任务。
- `--by-user` 只记录已经发生的用户决定，不产生批准。未取得决定时不能加此参数绕过状态限制。

## 4. 收尾与回执

按项目要求验证实际成果，保留失败和未验证项。需要独立审查时说明触发原因；普通小改动做相关验证，不机械增加完整复盘。

```text
python <技能目录>/scripts/tasks.py --dir <现有任务卡目录> receipt <任务ID> --receipt-id <本项目本任务本轮稳定编号> --status <任务状态> --summary <成果和证据> --verification <unverified或passed或failed或mixed> --next <下一步>
```

同一轮重试复用相同编号和内容，避免重复写回执；内容更正使用新编号并说明更正对象。回执、任务状态和交接的中断恢复使用：

```text
python <技能目录>/scripts/tasks.py --dir <现有任务卡目录> recover --receipt-id <原编号>
```

恢复只能补完已记录的同一次写入；若提示冲突，停止该任务的写操作并报告实际文件差异，不删日志、不改编号掩盖失败。并发锁只解决同一主机支持范围内的写入竞争，跨设备共享目录仍需单一写入主责。

字段与对接边界见 [回执格式](references/receipt-format.md)。本地任务回执不等于已上传，也不自动兼容某个接收端。项目另有上报协议时读取该协议、复用稳定编号并按实际权限处理；不重复上报或误记到挂载目录所属项目。

## 5. 交接与结束

优先在已有交接位置补充目标、有效决定、成果版本与路径、验证、剩余、授权和下一步。记录本轮实际核对的后台运行项、停止方法，以及尚待用户回答的问题和影响；没有则写无，未核对运行状态则写未验证。换窗时记录真实接手会话 ID；没有确认接手窗口时留为待定，不编造 ID。压缩上下文本身不要求换窗。

模板只补已有记录缺失的职责，不要求全部落盘：

- [任务卡](templates/task-card.md)
- [项目地图](templates/项目地图.md)
- [治理方案](templates/治理方案.md)
- [交接](templates/交接.md)

需要改名或 Git 操作时再读 [命名与 Git](references/naming-and-git.md)。交付简明说明已做动作、改动位置、验证结果、未完成项和下一步；有用户指定格式时遵守。任何平台动作、测试或人工验收都要分清已执行、失败、未验证。
