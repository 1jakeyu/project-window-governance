# 派发与模型选择

在委派临时子智能体、继续委派或向执行聊天下发任务前使用本引用。它指导如何遵循目标使用者的模型偏好，不替使用者设定一套固定模型，也不修改全局运行配置。

## 先判断执行方式、任务和现行偏好

- 先判断任务是否适合留在原聊天。需要独立交付、可以单独验收的工作可委派临时子智能体；不要为选模型额外拆任务。用户需要长期跟进的独立聊天，仍须明确建窗授权。
- 读取目标环境已经提供或已知入口中的用户与项目现行模型偏好，并核对本轮最新具体决定。遵守实际生效的规则层级；本轮已读且没有变化的内容可以复用，不为查偏好扫描其他项目或通读整份工厂记忆。
- 按任务的主要目标、依赖和实际难点选模型与思考深度，不因主聊天正在用某模型就一律继承。界面改动很小，但涉及复杂数据迁移边界时，应按数据与迁移难点判断；交叉任务不要只按“按钮”“截图”等表面词归类。
- 没有这类偏好时，依据当地工具实际可用的模型和任务需要说明选择，不自动采用下文示例。派发前用一句话说明任务类型及选型理由即可，不新增平行台账。

## 可复制的用户确认示例

下面来自一位使用者已经确认的协作偏好，供有同样需要的使用者确认后采用。它不是公开技能对所有使用者的默认清单，不代表官方性能排名、当前可用性或节省费用的证明。当地已经生效的偏好和最新具体决定优先。

| 主要任务 | 示例请求模型 | 示例思考深度 |
|---|---|---|
| 常规开发、修改与测试、Skill 维护、资料综合、结构化整理 | `gpt-6.1-sol` | `ultra` |
| 文案与图文整理、图片或图表理解、截图与版式检查、界面操作 | `gpt-6.1-terra` | `ultra` |
| 复杂故障、重要架构、矛盾证据裁决、复杂跨模块或跨项目取舍 | `gpt-6-astra` | `ultra` |

## 核对工具并实际传参

1. 读取当前委派工具的真实接口与限制，确认它能表达现行规则要求的模型和深度。只在提示词里写模型名或“使用 Ultra”，不算已经选择运行配置。
2. 当前 Codex `spawn_agent` 接口使用 `model` 与 `reasoning_effort`；显式覆盖模型时按接口要求使用 `fork_turns: "none"`。其他工具按其真实参数执行，例如某聊天工具可能使用 `thinking`，不能把字段原样套到全部平台。
3. 不继承完整历史时，提供任务目标、准确资料入口、允许范围、验收标准、现行模型偏好和继续委派约束。子智能体继续委派时仍须先判断执行方式与模型，并实际传参，不能因嵌套层级而跳过。
4. 复用已有子智能体前，核实它已知的模型与深度配置是否适合当前任务。跟进工具不能改模型时，不声称新提示词已经完成切换；缺少可信配置也不能假定符合偏好。确需另一配置时，在已授权范围内选择能满足要求的委派方式，并避免重复派工和重复写入。
5. 所需模型、深度或必要参数不可用，或无法按要求覆盖时，停止该次委派，说明具体限制；不静默换模型、降低深度或改全局配置绕过。与该次委派无关且已授权的工作可以继续。使用例外配置须有当地用户对该例外的明确决定。

例如，仅在使用者已经采用上表示例、任务属于常规开发且当前接口确实支持时，创建临时子智能体的参数片段可以是：

```json
{
  "model": "gpt-6.1-sol",
  "reasoning_effort": "ultra",
  "fork_turns": "none"
}
```

这只是模型相关的参数片段；真实调用还需工具要求的任务名称、目标和必要上下文。不要原样调用一个缺少任务的示例。

## 模型选择不产生操作授权

即使模型和深度都已经选好，仍分别检查具体动作的授权。只有用户明确要求时才创建用户可见的新聊天，只有明确授权向目标聊天发消息时才发送。未授权时保留可审查派发草稿，不自动建窗、广播或发消息，也不批量切换已有聊天的模型。

## 回执与跨项目采用

- 在项目已有任务记录或回执的文字字段中，简记请求模型、深度、理由及派发结果，无需为此变更任务卡或回执格式。有可靠平台运行证据才能记为实际模型；否则写“已请求，实际模型未核实”。工具接受调用、规则文件存在和实际运行模型是不同证据，子智能体自述不作为运行配置证明。
- 同一 Codex 用户配置下，可在其有效的全局 `AGENTS.md` 维护一份用户已确认的入口；仅将项目特有差异放入项目规则。工厂 `PROJECT_MEMORY.md` 只作需要细则、维护或冲突核对时的本机资料入口，不要求每个项目读取整份工厂记忆。
- 其他设备须由其用户在明确授权范围内采用适合本机的入口和偏好，不继承源设备的文件路径或操作批准。不能从一处写入推导所有已打开聊天已经重载、所有项目已经读取或所有设备已经同步；需要分别核验。
