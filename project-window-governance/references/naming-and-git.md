# 命名与 Git 操作

## 命名

先沿用项目既有命名规则。例如已有 `MMDD丨职责丨具体任务` 或 `项目｜职责｜任务` 均可继续使用；分隔符不同不构成治理问题。

标题应让用户看懂职责和当前工作。改名只在消除真实歧义时提出；不改真实会话 ID，不用标题代替主责或任务状态。平台返回的现有名称按原文展示，建议名称单独列出。

不要求每个项目或每个平台固定窗口数。窗口是否保留、合并职责或归档，要看未完任务、接手责任、有效交接及用户授权。标题相似、时间久、已压缩上下文都不能单独作为归档依据。

用户要求归档时列明准确平台、原始标题和真实会话 ID，说明影响及恢复方式；经授权调用正式平台工具并核对结果，不删除本地内部数据。

## Git

Git 不是窗口治理的必做步骤。先确认本轮是否确实改动代码或版本资料，以及用户与项目的现行规则。

需要了解已有改动时，可在准确仓库内只读查看状态和必要差异；不扫描其他仓库，不展示无关敏感内容。保留用户原有修改，区分本轮改动和历史改动。

以下操作分别依据真实授权执行：初始化仓库、新建分支或工作树、提交、变基、合并、推送、删除分支和回退。治理方案、任务收尾或“整理完成”不能自动授权这些动作；已有明确批准的操作无需重复询问。

确需提交时，只包含本轮已核对且获准的文件，先完成相关验证。不要自动执行 `git add .`，不要顺便提交用户原有修改。提交、推送和发布是不同动作；本地提交成功不代表已上传或部署。

恢复方案应指向具体备份、版本或平台恢复方式。没有授权时不执行强制覆盖、清理、重置或删除；遇到冲突保留现场并说明可选的具体修复操作。
